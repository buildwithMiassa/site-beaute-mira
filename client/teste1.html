Comprendre preventDefault, stopPropagation & les événements JavaScript

Oui — et c’est un concept très important en JavaScript côté navigateur. Le point subtil est qu’un événement comme click ne représente pas seulement « exécute mon code ». Le navigateur a aussi ses propres actions associées à cet événement.

1. Un clic déclenche plusieurs mécanismes

Prenons :

<a href="#contact" class="btn">Me contacter</a>

Quand tu cliques dessus, il faut imaginer quelque chose comme :

Utilisateur clique
       ↓
Le navigateur crée un événement "click"
       ↓
Les gestionnaires JavaScript sont appelés
       ↓
Le navigateur regarde si l'action par défaut doit être effectuée
       ↓
Si oui → navigation vers #contact

Ton code est donc une partie du traitement du clic, mais il n'est pas forcément le traitement complet.

2. preventDefault() agit sur une autre chose

Regarde :

heroActions.addEventListener("click", (e) => {
    e.preventDefault();

    console.log("Bonjour");
});

preventDefault() signifie :

« Pour cet événement, n'effectue pas l'action par défaut associée à l'élément. »

Il ne signifie absolument pas :

« Arrête le JavaScript ici. »

C'est une distinction fondamentale.

Par exemple :

e.preventDefault();

console.log("A");
console.log("B");
console.log("C");

affichera bien :

A
B
C

Donc preventDefault() n'arrête pas l'exécution du programme.

3. preventDefault() ≠ return

C'est là que ça devient intéressant.

Tu pourrais penser :

e.preventDefault();

veut dire :

return;

Mais non.

Ils ont des rôles complètement différents.

return

console.log("A");

return;

console.log("B");

Résultat :

A

Parce que return quitte la fonction.

preventDefault()

e.preventDefault();

console.log("A");
console.log("B");

Résultat :

A
B

Parce que preventDefault() n'arrête pas la fonction.

Il dit seulement au navigateur :

« N'exécute pas le comportement par défaut de cet événement. »

4. Dans ton exemple, qui fait quoi ?

Ton HTML pourrait être :

<div class="header__hero-actions">
    <a href="#about" class="btn">À propos</a>
    <a href="#contact" class="btn">Contact</a>
</div>

Et ton JavaScript :

heroActions.addEventListener("click", (e) => {

    const btn = e.target.closest(".btn");

    if (!btn) return;

    const targetHref = btn.getAttribute("href");

    if (!targetHref || !targetHref.startsWith("#")) return;

    e.preventDefault();

    const section = document.querySelector(targetHref);

    if (!section) return;

    section.scrollIntoView({
        behavior: "smooth"
    });
});

Lorsqu'on clique sur :

<a href="#contact" class="btn">

il y a deux acteurs :

Acteur 1 : ton JavaScript

Il dit :

section.scrollIntoView({
    behavior: "smooth"
});

→ « Fais défiler la page doucement. »

Acteur 2 : le navigateur

Il voit :

href="#contact"

et son comportement naturel est :
→ « Ah, un lien vers #contact. Je vais naviguer vers cette ancre. »

Tu ne veux pas que les deux travaillent.

Tu veux :

JavaScript → scroll fluide

et pas :

JavaScript → scroll fluide
+
Navigateur → navigation normale vers #contact

C'est exactement le rôle de :

e.preventDefault();

5. Pourquoi le navigateur fait-il ça après ton code ?

C'est une bonne question.

Ton gestionnaire :

heroActions.addEventListener("click", callback);

ne remplace pas le comportement natif du navigateur.

Il s'ajoute au système d'événements.

Tu peux imaginer :

             CLICK
               │
       ┌───────┴────────┐
       ↓                ↓
Ton JavaScript     comportement
                   par défaut
       │                │
       ↓                ↓
scrollIntoView()    href="#contact"

Avec :

e.preventDefault();

tu désactives la branche de droite :

             CLICK
               │
       ┌───────┴────────┐
       ↓                ↓
Ton JavaScript     comportement
       │              par défaut
       ↓                X
scrollIntoView()

6. Et ça ne concerne pas seulement les liens

C'est là que le concept devient vraiment utile.

<a>

<a href="https://example.com">Clique</a>

Comportement par défaut :
→ naviguer vers l'URL.

Tu peux faire :

link.addEventListener("click", (e) => {
    e.preventDefault();

    console.log("Je décide moi-même quoi faire");
});

Le navigateur ne naviguera pas.

<form>

Autre exemple extrêmement important :

<form>
    <input type="text">
    <button type="submit">Envoyer</button>
</form>

Quand tu soumets le formulaire, le navigateur a un comportement par défaut : soumettre le formulaire, généralement avec une navigation/requête.

Tu peux intercepter ça :

form.addEventListener("submit", (e) => {
    e.preventDefault();

    console.log("Je vais traiter le formulaire avec JavaScript");
});

C'est extrêmement courant avec les applications modernes.

Par exemple :

form.addEventListener("submit", async (e) => {
    e.preventDefault();

    const data = new FormData(form);

    // envoyer les données avec fetch()
});

Tu remplaces le comportement natif du formulaire par ton propre comportement.

7. Un autre concept important : stopPropagation()

Et là, beaucoup de débutants confondent les deux.

Tu as :

e.preventDefault();

et :

e.stopPropagation();

Ils n'ont pas du tout le même rôle.

preventDefault()

« Empêche l'action par défaut. »

stopPropagation()

« Empêche l'événement de continuer à se propager dans le DOM. »

Exemple :

<div id="parent">
    <button id="child">Clique</button>
</div>

Avec :

parent.addEventListener("click", () => {
    console.log("parent");
});

child.addEventListener("click", (e) => {
    console.log("child");
});

Quand tu cliques sur le bouton, tu peux avoir :

child
parent

Pourquoi ?

Parce que le clic sur button remonte dans l'arbre DOM.

C'est ce qu'on appelle la propagation de l'événement (event bubbling).

Si tu fais :

child.addEventListener("click", (e) => {
    e.stopPropagation();

    console.log("child");
});

alors :

child

et le parent ne reçoit pas cet événement par propagation.

Mais attention :

e.stopPropagation();

n'empêche pas le comportement par défaut du bouton/lien.

C'est justement pour ça qu'il faut bien retenir :

preventDefault()
    ↓
empêche l'action native

stopPropagation()
    ↓
empêche la propagation de l'événement

8. Et ton code utilise justement un autre concept très intéressant

Tu as :

heroActions.addEventListener("click", (e) => {

alors que les boutons sont probablement à l'intérieur de .header__hero-actions.

Tu n'as pas mis :

btn.addEventListener("click", ...)

sur chaque bouton.

Tu écoutes le clic sur le parent.

C'est ce qu'on appelle la délégation d'événement (event delegation).

Imaginons :

<div class="header__hero-actions">

    <a class="btn" href="#about">About</a>

    <a class="btn" href="#contact">Contact</a>

    <a class="btn" href="#projects">Projects</a>

</div>

Tu pourrais faire :

document.querySelectorAll(".btn").forEach(btn => {
    btn.addEventListener("click", ...);
});

Mais ton code fait plus intelligemment :

heroActions.addEventListener("click", (e) => {

    const btn = e.target.closest(".btn");

    if (!btn) return;

    // ...
});

Le clic arrive sur le bouton, remonte vers le parent, et le parent décide :

« Est-ce que l'élément qui a été cliqué correspond à .btn ? »

C'est très puissant lorsqu'on a beaucoup d'éléments dynamiques.

9. e.target et e.currentTarget

Et ton code permet aussi de comprendre une autre notion essentielle.

Tu as :

e.target

et :

e.currentTarget

Ils sont différents.

Supposons :

<div class="actions">
    <button class="btn">
        <span>Contact</span>
    </button>
</div>

Tu cliques précisément sur :

<span>Contact</span>

Alors :

e.target

peut être :

<span>Contact</span>

Parce que c'est l'élément réellement cliqué.

Mais :

e.currentTarget

sera :

<div class="actions">

Parce que c'est l'élément sur lequel ton addEventListener est attaché.

Donc :

e.target
    ↓
qui a réellement reçu le clic ?

e.currentTarget
    ↓
qui écoute l'événement ?

Et c'est précisément pour ça que :

e.target.closest(".btn")

est utile dans ton code.

10. Le modèle mental à retenir

Quand tu travailles avec les événements DOM, pose-toi toujours trois questions :

① Quel événement ?

  • click
  • submit
  • keydown
  • input
  • change
  • ...

② Quel est le comportement par défaut du navigateur ?

Par exemple :

<a href="..."> → navigation.

<form> → soumission.

③ Est-ce que je veux laisser le navigateur faire ce comportement ?

Si non :

e.preventDefault();

Et pour la propagation, demande-toi séparément :

« Est-ce que je veux que cet événement continue à remonter/descendre dans le DOM ? »

Si non :

e.stopPropagation();

Une phrase qui résume tout

preventDefault() ne contrôle pas l'ordre d'exécution de ton JavaScript. Il contrôle ce que le navigateur fait naturellement en réponse à l'événement.

C'est une distinction qui devient fondamentale dès que tu commences à faire des interfaces interactives avec les événements DOM.
